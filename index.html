Between kdb+ 3.6 and KDB-X, q gained more new grammar than in the previous decade: dictionary literals, assignments that take values apart and check them on the way in, functions that refuse bad arguments before their body runs, and a module system with its own rules for names. It also became stricter, and some code that ran for years now stops with an error. This document covers only that: the syntax, and the changes that break code. Every claim is a lab, run on KDB-X and set beside what KX's release notes say the same line did before, so you can see exactly what changed and when.

What Changed

Companion to the trilogy: The Order & Trade Lifecycle, Anatomy of a Fill and Sharded Ticks use this grammar; this document explains it.

1Why It Matters

For most of its life, q had one way to build a dictionary (k!v), one way to assign (name:value) and one way to check an argument (by hand, in the body).NUC. Not upwardly compatible: KX's term for a change after which some existing code behaves differently or stops working. Every NUC in this document is tagged. kdb+ 4.1 changed all three. A dictionary now has a literal form, ([a:1;b:2]). The left side of : can be a pattern that takes a value apart, checks its types and transforms it, and a failed match assigns nothing at all. The same patterns work in a parameter list, so a function can refuse a bad argument before its body runs. KDB-X then added modules: code with a private namespace, loaded with use and given whatever name the caller chooses.

The new syntax is not decoration. A tickerplant's upd that checks its table name in the parameter list cannot log a message for a table that does not exist; a config loader that types its settings by pattern cannot start a process on port 0N. The other half of the story is that q became stricter. Some of what 3.x accepted is now an error, often at parse time, and some results changed quietly. The checklist at the end lists every one.

Literals

A table always had a literal, ([]a:1 2;b:3 4), and a keyed table had ([k:…]v:…). The dictionary, the structure both are built from, did not: you wrote `a`b!1 2, and a one-key dictionary needed two enlists. 4.1 closes the gap with the same bracket grammar, and every rule of the table literal carries over: bare names take their values from variables, omitted values make a projection, and omitted names are generated.

A1Dictionary Literals

4.1

([k:v;…]) is a dictionary with symbol keys, and ~ to the ! form. The win is largest for one key, where enlist[`a]!enlist 1 becomes ([a:1]), and for building a dictionary from variables, ([a;b]).

An omitted value, ([a:101;b:]), is a projection waiting for it: apply it to a list of values with each and you get a table, one row per value.

Keys must be valid q names, so ([10:`a]) is 'type; use ! for anything else. A duplicate key is not an error: q renames it (a, a1), so a typo silently adds a key. And a file handle as a value needs parentheses: in ([log:`:./log]) the `: reads as the start of an assignment and the line fails with 'assign; ([log:(`:./log)]) works.

Patterns

From 4.1, the left side of : can be a pattern: a list, a dictionary or a table of smaller patterns, any of which can be a name, a constant, a type check or a filter function.Destructuring. The name other languages give to taking a value apart on assignment. Python's a, b = 1, 2 is the list case; q adds dictionaries, tables, types and filters. The whole value is checked before anything is assigned, which is the property everything else in this section relies on: a failed match changes nothing.

B1Destructuring

4.1

A list pattern takes a list apart by position, a dictionary pattern by key, a table pattern by column. An empty item matches anything; a constant must match exactly, and is how a pattern says “only if this is a fill”.

Watch y: it was `untouched before the failed match and is still `untouched after it. That is the guarantee.

Only ! and flip may appear as operators in a pattern, because they are the two that can be undone: (m!n):d takes a dictionary apart into keys and values.

B2Types & Filters

4.1

name:`s checks a type: lower case for an atom, upper case for a list. A filter function, x:f, is applied to the value first and the result is what gets matched and assigned, so a filter can validate (tempCheck signals), convert (10+), or both. chkVals does both and changes the type on the way: sumVals is called with a string and its body sees a list of longs, or never runs at all.

In a parameter list the same patterns guard a function: fluxCapacitor refuses a non-float speed before its body runs, and {[x;]x} marks the second argument as unused.

The trap is the last three lines. Inside a dictionary pattern, k:`s is the constant `s, matched against the value; the type check needs a name in front, k:k:`s. KX's own reference spells this out because everyone gets it wrong once.

B3The Pattern Conditional

4.1

:[v;p1;r1;p2;r2;…;default] matches v against each pattern in turn and returns the result beside the first that fits. Only that result is evaluated.

Where $[…] asks a question of a value, :[…] asks what shape it has. route sends a message by the keys it carries, which is the dispatch every feed handler writes by hand.

B4Caught at Parse Time

4.1NUC

Making the left side of : a grammar meant deciding what it may not contain. Each line here was accepted before, or did something surprising; now each is refused when the code is read, not when it runs, which means a script with one of them in a function that is never called still fails to load.

([]a::e) used to amend a global a while building a column; it is now 'parse. do:1 and an assignment to if[…] are 'assign (4.1 2025.11.25). {x}[;1], a projection with more arguments than the function takes, is 'rank.

exit:1 is also 'assign now, but it is left out of the lab: on a version that accepts it, the runner could no longer exit.

Stricter Semantics

These are not new grammar but old grammar with new answers. They matter more than the new features, because a feature you do not use cannot hurt you, and a changed result in code you already run can.

C1qSQL Tightened

4.04.1NUC

4.0 made a column named like a group, select a,b by a, a parse error (dup names for cols/groups) instead of quietly renaming it; a column repeated among the columns is still renamed, as a1. It also made aggregates over a by agree for atoms, and made lj insist on a keyed table on the right.

4.1 made update … by on a dictionary an error rather than ignoring the by, and fixed a scoping bug from 2.6: value inside select or exec now reads globals, so the lambda's local a:1 is no longer seen.

The value change is the dangerous one: no error, a different number. Search your code for value" inside qSQL.

C2Numbers, Bytes & Guids

4.1KDB-XNUC

The theme is null, not garbage. A float-to-int conversion out of range, including 3i div 0i, now gives 0Ni on every platform (ARM used to give 0i); a string-to-time cast that overflows gives null instead of a wrapped value; short parsing no longer clamps to 0Wh.

Bytes became first-class text: vs and sv take byte vectors, ss searches them, and .Q.atob decodes base64. Guids gained an order, so min, max and asc work, with 0Ng smallest.

Two long-standing wrong answers were fixed too: x*/y on bytes or shorts (wrong since 3.3) and the seed of &/ on a sorted list (ignored since 3.1). If a result moves in the KDB-X column here, it was wrong before.

Names

A namespace is a dictionary of names hanging off the root: .foo.f is f in .foo. The rule that governs code is about when an unqualified global name is resolved: an unqualified global is bound to the current namespace in effect at the point of the function definition,Q for Mortals 4.1, §12, “Fact of Life #4”. The function body does not show which namespace it was bound to; value on the function does. not where it is called from. Modules depend on this rule, and add one exception that catches everyone.

D1Namespaces

4.xKDB-X

Four questions, each one line. Is a global bound when the function is defined? (.foo.f 1.) Is a name the namespace lacks found in the root? (.foo.g[], defined under \d .foo, against .foo.h[], defined from the root.) Can \d go two levels deep? Can a namespace be deleted?

Q for Mortals says \d can only go one level down from the root. On KDB-X 5.0 2026.10.23 it goes two: \d .a.b works and \d reports `.a.b. No release note mentions the change.

q.foo)k:{…} defines a function in .foo without leaving the root, the safest way to write one: no \d to forget to undo.

The root-fallback question, answered for KDB-X. It is often said that KDB-X stopped finding root names from inside a namespace. On KDB-X there is no fallback: .foo.g, defined under \d .foo, signals 'rootOnly, while .foo.h, the same body defined from the root, returns 42. The name was bound to the namespace the function was written in, and .foo has no rootOnly. Whether that is new is a separate question: no release note lists a change to name lookup, and the behaviour is exactly the definition-time binding Q for Mortals describes for kdb+. The claim most likely confuses this rule with the qSQL rule inside modules. It could not be run on kdb+ 4.x here; one run with a 4.x licence settles it.

Modules

A script loaded with \l puts its names wherever it likes, usually the root or one namespace it assumes nobody else uses. A module runs in a namespace of its own, decides what to show through a variable called export, and is loaded with use, which returns that export for the caller to name: os:use`kx.os.kdb+ 4.x. Modules are KDB-X only: on kdb+ 4.1, use is not a built-in, so use`kx.os fails as an undefined name. KX says its open-source modules are incompatible with earlier versions of kdb+. The labs in this section therefore have one column. Modules load once and are cached; the second use returns the same export.

Three things follow from the namespace being private. A module cannot define a name q reserves (log, load, parse, use) as a bare name, so it defines .z.m.log instead; .z.m is the module's own namespace and .z.M its name as a symbol. A function that needs to amend the module's own state by name writes .z.M.w, not a hard-coded `.u.w. And submodules are named relative to the file that uses them: `.child, `..sibling, `...parentSibling.

The three modules here are built for the tickerplant, which is why they share the prefix tick.. KX prefixes its modules kx. and Data Intellect's community modules use di., so tick. cannot collide with either. Their layout follows Data Intellect's convention, code and tests in one directory per module, and their tests use KX's Unit Test module, kx.test.

Beyond Syntax: Virtual Tables

One module changes what a table is without changing a word of the q you write against it. kx.pq.t builds a virtual table over data already on disk, Parquet files or a directory layout of your own, from a catalogue of partitions (mkP). Directory names such as a date or an instrument become virtual columns, so a where on them prunes whole partitions, and Parquet row groups are pruned too. The point for this document is what stays the same: select … where date=…, sym=… reads exactly as it does against a classic date/table/column HDB.

That makes it an architecture question, not a grammar one: a layout partitioned by date and sym, and intraday data written straight to disk and queried beside history. It gets a document of its own; until then, start with Data Intellect's Virtual Table Starter Pack, their TorQ-Virtual-Tables overlay, and KX's Parquet reference.

·Four Rules

1

Check at the boundary

A filter in a parameter list runs before the body and a failed pattern assigns nothing. Put the checks where data enters, upd, an API, a config loader, and the rest of the code can trust what it is given.

2

Use the dictionary literal

([a:1]) over enlist[`a]!enlist 1; options as one dictionary argument over positional flags. But keys must be names, and a duplicate key is renamed, not refused.

3

Qualify across namespaces

A global binds where the function is defined. Define from the root with full names, or with q.ns); in a module, qualify qSQL function names with .z.m.

4

Read the NUCs for silent changes

A parse error finds itself. The changes to fear are the ones that return a different number: value in qSQL, aggregates over by, casts that now return null.
